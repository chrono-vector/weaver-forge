J0-only/Popen remains a historical comparison, not a selected path.

J1 is built before the target `CreateProcessW` and is included in the creation attribute list. No permitted branch creates the target first and assigns J1 later. Assign-after-create and fallback create do not satisfy either hop. `JOB_LIST` contains J1 only on the target hop and is a different attribute from `HANDLE_LIST`. The J1 handle is non-inheritable and is not a `HANDLE_LIST` member. J0 and J1 require `KILL_ON_JOB_CLOSE` and neither `BREAKAWAY_OK` nor `SILENT_BREAKAWAY_OK`. `CREATE_BREAKAWAY_FROM_JOB` stays prohibited. The controller and the target must not receive an inherited J0 handle. Intended J1 ownership is the controller alone, and that ownership is unproven.

### C-12. Independent Supervisor

LABEL: EXISTING_FROZEN_RULE_UNCHANGED

The Supervisor provides the outer independent wall-clock monitor and terminates on its own deadline if the controller stays alive but stops. A Job CPU-time limit remains only a backstop and is not a substitute. If that monitor cannot be guaranteed, refuse before spawn. Supervisor readiness must be confirmed by the Supervisor itself.

### C-13. No retry and no relaxed fallback

LABEL: EXISTING_FROZEN_RULE_UNCHANGED

After any failure, retry, re-create, relaxed-environment relaunch, Popen fallback, and assign-after-create fallback remain prohibited. Refusal does not substitute `NUL`, `DEVNULL`, a null standard-handle pointer, an invalid-handle sentinel, `bInheritHandles=FALSE` without the list, or a create that omits `HANDLE_LIST`. One failed close, one failed create, or one refused Resume does not start a second attempt. EB-5 already forbids retry under a relaxed environment or policy.

### C-14. Fail-closed ownership

LABEL: EXISTING_FROZEN_RULE_UNCHANGED; EVIDENCE_REQUIRED_BEFORE_ACTIVATION

If target-to-controller handle-duplication prevention and ownership cannot be proven, refuse launch. A Job DACL, an unnamed handle, or a non-inheritable flag is not that proof. The refusal rule is closed. The proof is not. Every pipe, attribute allocation, Job, and process or thread handle keeps one documented owner and one closure point. Concurrent process creation and temporarily inheritable handles still require a reviewed race policy. That policy remains unwritten. Unverified cleanup is non-success. A successful terminate return, root exit, or one active-process query is not confirmation. The cleanup claim stays limited to confirmed Job-associated processes.
